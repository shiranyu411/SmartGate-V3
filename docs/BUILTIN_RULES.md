# SmartGate V3 Built-in Rules

This document describes the rules and remote rule-set defaults shipped by
SmartGate V3. The normative HTTP shapes remain in `docs/API_CONTRACT.md`; the
implementation authority is `internal/state` and the data-plane emitters under
`internal/fabric` and `internal/singbox`.

## Local catalog

A fresh Spec starts with a complete catalog of seven local groups. The
catalog is represented as individual rules in `GET /api/rules`, with
`source: "builtin-v2"`. The built-in target mapping is:

| Group | Default behavior |
| --- | --- |
| `direct` | Sends `home.arpa`, `lan`, and `local` to `Direct`. |
| `generalproxy` | Empty by default; user entries use the general business pool. |
| `streaming` | Sends `netflix.com`, `disneyplus.com`, and `youtube.com` to the streaming pool. |
| `ai` | Sends curated AI product domains and narrow product keywords to the AI pool. |
| `banking` | Sends a conservative set of bank, identity, tax, payment, and brokerage domains to the banking pool. |
| `crypto` | Sends a conservative set of exchange, wallet, on-ramp, and custody domains to the crypto pool. |
| `block` | Empty by default; use a small, reviewed host list or the optional ad rule-set. |

The full current list is generated by `internal/state.DefaultRuleSpecs()`;
the table intentionally summarizes behavior rather than duplicating a long
list that can drift from the binary. Use `GET /api/rules` to inspect the exact
catalog on a running installation.

Local matchers support:

- `domain_suffix`: a normalized domain suffix;
- `domain_keyword`: a normalized substring matcher, intended only for narrow
  product terms;
- `ip_cidr`: an IPv4/IPv6 CIDR or a single IP, normalized to `/32` or `/128`.

Domains are lower-cased, trimmed, and de-duplicated. A single IP is treated as
the corresponding host prefix, including IPv4-mapped IPv6 input. `geosite` and
`geoip` entries are catalog metadata for remote rule-sets, not local hand
lists.

## Remote default sets

The default remote catalog contains three sets:

| ID | Default target | Default state |
| --- | --- | --- |
| `geosite-category-ads` | `block` | Disabled; ad-block master switch is also disabled. |
| `geosite-cn` | `direct` | Available but disabled; enables CN domain direct behavior when explicitly selected. |
| `geoip-cn` | `direct` | Available but disabled; enables CN IP direct behavior when explicitly selected. |

All three use binary sing-box `.srs` format, a `24h` update interval, and
`Proxy` as the download detour by default. Production routers should prefer
local `.srs` paths under `/etc/sing-box/rule-set/` so startup and refresh do
not depend on an external download.

The default memory guard is deliberately conservative:

| Limit | Default |
| --- | ---: |
| Maximum enabled sets | 12 |
| Maximum total bytes | 8 MiB |
| Maximum bytes per set | 4 MiB |
| Warning total | 5 MiB |
| Warning enabled sets | 8 |

The guard is checked before a candidate is applied. Warnings are surfaced in
rule-set views; hard limits reject an oversized candidate rather than risking
router memory pressure.

## Priority and conflicts

User rules are stored in Spec and have higher priority than built-in and GEO
defaults. An enabled user rule with the same matcher kind and value marks the
matching system rule as `overridden_by`; the system rule remains visible for
explainability but is not compiled into the Fabric.

Two enabled user rules with the same matcher assigned to different pools are a
conflict. The catalog can be saved so the operator can review and resolve it;
the save operation does not silently choose a winner. Use
`POST /api/rules/resolve-conflict` with a `keep_pool` value to disable the
other conflicting user rules. Until every conflict is resolved:

- `POST /api/config/dryrun` is blocked;
- `POST /api/config/apply` is blocked independently, including a direct call
  that bypasses a previous dry-run;
- the API returns `rule_conflict_unresolved` and includes the conflict data.

This prevents a saved but ambiguous catalog from reaching the running data
plane.

## Fresh install and Route Explain

`scripts/install.sh` selects the transactional fresh bootstrap only when the
target is blank. The bootstrap creates a V3 Spec with the built-in local
catalog and the three default remote sets. Existing or partial installations
are never bootstrapped over: `install.sh` routes healthy existing installs to
`scripts/deploy-safe.sh` and fails closed on ambiguous residue.

After first boot, `GET /api/rules` shows built-in entries and their source,
while the Routes page displays the same complete catalog. `POST
/api/routes/explain` reports the matched rule, source, pool, and ordered
decision chain, so operators can distinguish a built-in match, a user override,
and a GEO rule before applying configuration.

## Operational guidance

- Keep hand-authored local lists small and reviewable; use `.srs` for large
  geo/ad data.
- Do not enable the remote ad set merely to obtain a general geosite catalog.
- When `geosite-cn` is enabled, SmartGate inserts its Google/GFW proxy-safety
  exceptions before CN direct matching.
- A Spec edit changes desired state only. Always run dry-run, inspect the
  result, and then apply it before expecting traffic to change.
